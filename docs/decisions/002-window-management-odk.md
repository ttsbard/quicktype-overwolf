# ADR-002: Public Native API для окон, ODK — изолированная оценка

## Контекст

[ROADMAP-004](../roadmap/active/004-window-management-odk.md) требует надёжного фокуса, восстановления геометрии/DPI и режима Bottom center. QuickType загружается из исходников, имеет три фиксированных окна и не требует npm для запуска. Минимальная версия клиента — 0.250.0.

## Проверка опубликованного ODK

2026-10-23 через npm registry получен `@overwolf/odk-ts@1.1.2` (Node >=22), определения `@overwolf/types@3.51.1`. Node машины разработки — 24.13.0. Зависимости установлены с `--ignore-scripts` только в `.work/odk-evaluation/`.

[Воспроизводимый прототип](../../tools/odk-evaluation/README.md) выполнен на синтетических ответах Native API, не в игре. Результаты:

- `Windows.Self()` и `Windows.FromId()` — асинхронные методы с заглавными буквами; примеры `self/fromId` из обзорной страницы не соответствуют этой версии.
- Обёртка существующего окна через `FromId` работает после инициализации общего `___odkinternal___`. В проверенном plain Native окружении без этого реестра вызов завершился `TypeError`. ODK-возможности не следует подключать к объявленным окнам без адаптации жизненного цикла.
- `bringToFrontWithFocus()` вызывает обычный `overwolf.windows.bringToFront(id, true, callback)`. Новая гарантия захвата ввода не обнаружена.
- `MonitorHelper` на публичной структуре Display (`x/y/width/height/dpiX`) без поля `workingArea` завершился `TypeError`. На реальном новом клиенте дополнительные поля могут присутствовать; это проверка зависимости от расширенного контракта, не утверждение о повсеместной поломке ODK.
- ODK использует `overwolf.windows2` для событий и `overwolf.windows.setBounds` для геометрии. Последнего метода нет в публичной документации `overwolf.windows` и namespace windows из `@overwolf/types@3.51.1` (одноимённый метод mediaPlayerElement — другой API).
- Из прототипа собран и синтаксически проверен браузерный IIFE-bundle через `esbuild@0.25.12`: 62 579 байт с minify, target Chrome 125. Он находится только в `.work/`, не подключён к QuickType. Для добавления ODK понадобились бы подготовка browser bundle, учёт зависимости и отдельная проверка поддерживаемых клиентов.
- Типы OSRWindowOptions содержат `grabKeyboardFocus`, `takeOverAction`, `takeOverReleaseHotkey`, прозрачность и desktopOnly; семантика относится к созданию новых окон. Это не доказательство миграции всех manifest-настроек существующего окна без изменений.

## Решение

Использовать прямой публичный Native API и собственный небольшой адаптер `window-geometry.js`. ODK в рабочее приложение не включать. Пользовательские улучшения внедрить полностью без обязательного перехода на TypeScript/npm и без повышения минимальной версии клиента.

Изменения размера и позиции сериализуются: объектная перегрузка `changeSize({window_id, width, height, auto_dpi_resize:true}, callback)` → проверка результата → `changePosition(windowId, left, top)`. Используются логические единицы публичного DPI-aware API, возвращаемые `getCurrentWindow`: повторное масштабирование размера/позиции исключено. Физические границы мониторов переводятся в эти единицы для расчётов. Размер игры берётся из `logicalWidth/logicalHeight`, с fallback на обычные размеры и DPI. Старые сохранения также получались из `getCurrentWindow` и читаются без умножения; новые имеют `coordinateSpace: logical` и диагностические метаданные DPI/контекста.

Документация API пишет «with DPI conversion», а обзор DPI явно указывает, что значения `getCurrentWindow` нужно передавать назад без масштабирования. Выбран именно публичный [DPI-гайд](https://dev.overwolf.com/ow-native/guides/dev-tools/windows/windows-resolution-size-and-position/). Расширенные дескрипторы ODK/windows2 с `logicalBounds` — отдельный контракт. Для hybrid OSR гайд отмечает зависимость от DPI основного монитора; адаптер учитывает это при отсутствии расширенного `dpiScale`. Работа смешанных DPI требует реальной приёмки, а не выводов по синтетическим тестам.

`setBounds` намеренно не вызывается по одному наличию функции: публичная сигнатура и минимальная версия не подтверждены. Документированный fallback стал основным вариантом. Операции не атомарны, поэтому краткое промежуточное положение требует отдельной визуальной проверки.

Для мониторов используется `getMonitorsList` (0.83, требует `DesktopStreaming`); permission добавлена в манифест только для чтения геометрии. Запись/захват экрана не реализованы. Используется `workingArea`, когда оно присутствует; иначе — публичный прямоугольник Display. Поэтому исключение taskbar на клиенте без `workingArea` не гарантировано. При недоступности API применяется текущий `screen.avail*`; неизвестная геометрия не заменяется выдуманным разрешением.

`getRunningGameInfo2` (0.188), `getMainWindow` (0.113), `onScreenPropertyChanged` (0.143), `changeSize`/`changePosition` и `requestOverlayFocus` (0.250) укладываются в существующий минимум 0.250.0. Новых Node-требований к приложению/CI нет.

## Последствия и проверка

- Свободная позиция остаётся по умолчанию. Режим Bottom center и отступ применяются после Save; ручное перемещение отключает привязку. Сброс центрирует окно, снимает ручную геометрию и включает авторазмер.
- Расчёты, API-ошибки, отложенные операции, очередь и интеграция с настройками покрыты регрессионными тестами. ODK-прототип проверяет контракт и browser build, не работу реального оверлея.
- [Ручной приёмочный лист](../development/window-management-acceptance.md) остаётся пользователю: игры, раскладки, fullscreen/OOPO, реальный DPI и несколько мониторов. Отсутствие игровых результатов не объявляется исправленным захватом фокуса.
- Повторно рассмотреть ODK при документировании нового контракта для поддерживаемого минимального клиента, необходимости динамических окон и подтверждённых преимуществах в реальной матрице QuickType.
