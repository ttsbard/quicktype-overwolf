# ROADMAP-004: Надёжное управление окнами и оценка ODK

## Цель

Сделать открытие, скрытие и восстановление QuickType предсказуемыми: окно получает ввод при вызове, не перехватывает его после скрытия и остаётся доступным после смены монитора, разрешения или DPI. Оценить ODK на конкретных сценариях приложения и затем принять решение о внедрении.

Статус `planned`: исследование документации выполнено, реализация и игровые проверки ещё не начаты. Эта roadmap не подтверждает исправление потери фокуса при смене раскладки.

## Исходные факты

- Приложение: обычные HTML/JavaScript, три объявленных окна (`background`, `overlay`, `desktop`), загрузка напрямую из `quicktype-overlay/`.
- В `background.html` открытие состоит из `restore`, `bringToFront(..., true)`, `requestOverlayFocus` и IPC. Используются общий `switching`, таймер 1200 мс и страховочный запрос фокуса через 60 мс; результаты части операций не проверяются.
- В `overlay.js` поле повторно запрашивает фокус сразу и через 15/45/100/200 мс. Таймеры проверяют видимость, но не поколение открытия: старая попытка может попасть в уже новую видимую сессию.
- Геометрия сохраняется абсолютными координатами; восстановление ограничивает размеры фиксированными пределами, но не проверяет актуальную доступную область. Сброс задаёт 640×100 и позицию (100, 100).
- На машине разработки проверена установленная версия Overwolf `0.311.1.1`. Минимальная версия приложения в манифесте — `0.250.0`; повышение минимума требует отдельного обоснования совместимостью API.
- ODK предлагает Promise-операции, позиционирование, DPI и привязку. В изученном исходнике `bringToFrontWithFocus()` оборачивает существующий `overwolf.windows.bringToFront(id, true, callback)`; это не доказательство нового механизма захвата ввода.

## Порядок реализации

Каждый этап — отдельное локальное изменение с проверкой перед следующим. Начать с этапов 0–1 на существующем API; решение об ODK принять на этапе 4.

### Этап 0. Зафиксировать исходное поведение

- [ ] Через [Docs MCP](../../development/overwolf-docs-mcp.md) проверить Native API для фокуса, состояний, `setBounds`, мониторов и DPI; сверить необходимые версии клиента.
- [ ] Записать игру, графический API, оконный режим, раскладки, разрешение и DPI для воспроизводимого случая потери фокуса.
- [ ] Пройти базовую матрицу ниже на текущем приложении и сохранить наблюдения. Не считать отсутствие второго монитора или игры успешным тестом.
- [ ] Проверить доступность `overwolf://api-tracing` под developer account. При доступности использовать для порядка вызовов и ошибок; не записывать REST payload и авторизационные данные.

Готовность: есть исходный сценарий и результаты, позволяющие сравнить эффект изменения. Не менять GamesList или настройки игры автоматически.

### Этап 1. Управление жизненным циклом и фокусом

- [ ] Ввести явное желаемое состояние и номер операции/поколения открытия. Запоздалые callbacks и таймеры предыдущей операции не должны снова активировать скрытое окно или новую сессию ввода.
- [ ] Координировать показ/скрытие/повторный вызов из контроллера, исключить пересечение операций после произвольного таймера `switching`.
- [ ] Обрабатывать ошибки `restore`, `bringToFront`, `requestOverlayFocus`, IPC и скрытия. Ограниченный timeout должен освобождать управление и позволять повторный вызов, без бесконечных повторов.
- [ ] Разделить системный захват фокуса и DOM-фокус поля. Согласовать контроллер и оверлей; сокращать страховочные повторы только после сравнения поведения в игре.
- [ ] Добавить регрессионные проверки на быстрый show/hide/show, поздний callback, отказ API и отсутствие callback, а также сохранность черновика и активного REST-запроса.

Готовность: после скрытия старые операции не возвращают фокус; новый вызов работает после отказа/timeout; Enter и Escape сохраняют текущую семантику. Реальный возврат управления игре подтверждён ручной проверкой.

### Этап 2. Восстановление видимой геометрии

- [ ] Определять доступную область отдельно для рабочего стола и активной игры; учитывать рабочую область монитора, отрицательные координаты и различие физических/логических единиц.
- [ ] Восстанавливать сохранённое положение, если оно доступно. Если монитор отключён или окно вне доступной области, переносить его в видимую область и ограничивать размер её размерами.
- [ ] Заменить безусловный сброс в (100, 100) осмысленным размещением в текущем контексте, например по центру. Зафиксировать окончательный вариант в пользовательской инструкции.
- [ ] Использовать `setBounds` для совместного изменения размера и позиции, если совместимость подтверждена. Учесть `auto_dpi_resize`; при необходимости оставить проверенный fallback на старых клиентах.
- [ ] Обновлять сохранённую геометрию только после успешной операции. Сохранить различие ручного размера и автоматической высоты, совместимость старых настроек и независимое сохранение параметров подключения.
- [ ] Покрыть расчёт геометрии тестами: отключённый монитор, отрицательные координаты, маленькая область, масштабирование, ошибка API.

Готовность: окно и его управляющие элементы доступны после смены конфигурации экрана; сброс и авторазмер работают, старые настройки читаются.

### Этап 3. Необязательная привязка к краю

- [ ] Добавить явный выбор свободного размещения или привязки снизу по центру с отступом; текущим пользователям сохранить свободный режим по умолчанию.
- [ ] В режиме привязки пересчитывать позицию после автоматического изменения высоты и смены доступной области. Ручное перемещение должно переводить окно в свободный режим и сохранять новое положение.
- [ ] Проверить перенос длинного текста, скрытие/открытие, Reload, смену DPI и разрешения; обновить настройки и документацию режима.

Готовность: привязка не мешает вводу и не борется с ручным перетаскиванием. Можно отложить этот этап независимо от исправлений этапов 1–2.

### Этап 4. Изолированная оценка ODK и решение

- [ ] Зафиксировать конкретную доступную версию `@overwolf/odk-ts` и её типы. Не полагаться на `main` как на опубликованный пакет. Изученный `package.json` на `main` содержит `1.1.2` и Node >=22; текущий CI проекта использует Node 20.
- [ ] Проверить действительные сигнатуры: обзор показывает `Windows.self()/fromId()`, изученный исходник — асинхронные `Windows.Self()/FromId()`. Проверить поддержку оборачивания существующих объявленных окон.
- [ ] Проверить сохранение всех нужных параметров: прозрачность, видимость на desktop/в игре, `grab_keyboard_focus`, takeover `ReleaseOnHidden`, release hotkey, размеры и taskbar.
- [ ] Сделать локальный прототип вне подключённой папки `quicktype-overlay/`. Оценить подготовку браузерного JS, зависимости, воспроизводимость и возможность продолжать загрузку unpacked. Не собирать ZIP/OPK.
- [ ] Сравнить на той же матрице: надёжность фокуса, геометрия/DPI, число дополнительных вызовов, обработка ошибок, сложность сопровождения.
- [ ] Записать решение: внедрить ODK частично/полностью либо оставить прямой API. Полный перенос на TypeScript и динамическое создание всех окон не являются условием выполнения roadmap.

Готовность: решение обосновано результатами; перенос в рабочее приложение — отдельный небольшой шаг после успешного прототипа. Есть простой откат к предыдущему рабочему варианту.

## Матрица ручной проверки

Для каждого выполненного сценария фиксировать версию приложения/Overwolf, окружение, ожидаемый и фактический результат. Непроверенные варианты отмечать явно.

| Сценарий | Ожидаемый результат |
|---|---|
| Desktop: запуск, значок хаба, настройки | Окна открываются, доступны и не создаются повторно |
| Игра: borderless и fullscreen, если поддерживается | Хоткей открывает ввод; Enter/Escape возвращают управление игре |
| Быстрый хоткей, скрытие до callback, повторный вызов | Финальное состояние соответствует последнему действию; поздний фокус не возвращается |
| Alt+Tab, потеря фокуса, RU/EN при открытом поле | Нет нового перехвата после скрытия; поведение раскладки сравнивается с исходным |
| Медленный/ошибочный REST, скрытие и новое открытие | Черновик сохранён; старый ответ не стирает новый ввод и не закрывает новую сессию |
| Один/два монитора, монитор слева, отключение второго | Оверлей и настройки остаются доступны |
| DPI 100%/150%, разные DPI экранов, смена разрешения | Положение и размеры осмысленны; окно не выходит за доступную область |
| Ручной ресайз, несколько строк, сброс, Reload | Геометрия сохраняется; автоматическая высота не превращается в ручную случайно |
| OOPO / trusted fullscreen без интерактивного ввода | Ограничение платформы зафиксировано; отображение не выдаётся за работающий захват ввода |

## Проверки и завершение

- Синтаксис изменённых JS и встроенного скрипта `background.html`, целостность JSON и ресурсов манифеста, `node --test tests/regressions.test.cjs`.
- Тесты со заглушками подтверждают управление состоянием и геометрию, но не реальный exclusive focus. Игровую проверку выполнять после ручного Reload unpacked extension совместно с пользователем.
- Новые API и зависимости не должны молча повышать минимальные требования. Итоговый минимум и CI обновляются только при обоснованной необходимости внедрения.
- Обновить инструкции и changelog по фактическому результату. Перенести roadmap в `completed/` с Outcome после реализации обязательных этапов, решения по ODK и фиксации результатов ручных проверок; отложенные функции обозначить явно.
- Работа локальная; push и сборка дистрибутива — только по прямому запросу пользователя.
