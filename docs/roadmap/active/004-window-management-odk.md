# ROADMAP-004: Надёжное управление окнами и оценка ODK

## Цель

Сделать открытие, скрытие и восстановление QuickType предсказуемыми: окно получает ввод при вызове, не перехватывает его после скрытия и остаётся доступным после смены монитора, разрешения или DPI. Оценить ODK на конкретных сценариях приложения и затем принять решение о внедрении.

Статус `in_progress`: реализация этапов 1–3 и оценка ODK завершены. Осталась ручная приёмка в играх и на физических мониторах, которую пользователь выполняет после всей реализации. В `completed/` документ будет перенесён после её результатов; новый захват фокуса пока не объявляется подтверждённым.

## Результат реализации на 2026-10-23

- Жизненный цикл: поколение операций, таймауты, проверка API/IPC, восстановление последнего намерения после позднего native-вызова. Системный фокус принадлежит контроллеру; DOM-повторы отменяются/проверяются при скрытии, новом открытии и переходе в настройки. Stale IPC сверяется через getMainWindow с текущим намерением контроллера.
- Геометрия: адаптер window-geometry.js с сериализацией изменений, определением области desktop/игры, восстановлением потерянного окна, отрицательными координатами, ограничением размера и DPI-метаданными. Старые настройки читаются без двойного масштабирования; автоподбор высоты и ручной resize разделены. Сохранение — после успешных операций, reset центрирует и возвращает авторазмер.
- Bottom center и отступ добавлены в настройки с явным Save; новые пользователи и старые установки остаются в Free position. Ручное перемещение отключает привязку, ресайз сохраняет её.
- Опубликованный ODK 1.1.2 установлен и проверен в изолированном прототипе; браузерный bundle подготовлен только в .work/. [ADR-002](../../decisions/002-window-management-odk.md): оставить public Native API, без npm/build в приложении. Причины: тот же native-фокус, расширенный windows2/setBounds-контракт и дополнительные условия обёртки существующих окон/мониторов.
- Вместо неподтверждённого публичного setBounds используется документированный последовательный fallback changeSize/changePosition. Минимум Overwolf 0.250.0 сохранён; DesktopStreaming добавлен для списка мониторов, захват экрана не реализован.
- Автоматические проверки и сценарии интеграции покрывают геометрию, очередь, DPI, ошибки, сохранность настроек, autoheight и режим привязки. Интерфейс проверен в браузере; реальные игры не тестировались.
- Итоговый прогон: 88/88 тестов; синтаксис JS/встроенных скриптов, ресурсы HTML/манифеста, ссылки Markdown и PowerShell AST проверены. В браузере подтверждены выбор Bottom center, Save и восстановление отступа 40 после Reload. ZIP/OPK не собирались.

[Приёмочный лист](../../development/window-management-acceptance.md) содержит все оставшиеся ручные сценарии, исходные параметры окружения, API tracing и фиксацию дефектов. По прямому указанию пользователя они выполняются после реализации, а не блокируют разработку.
## Исходные факты

Ниже зафиксировано состояние до реализации; текущий результат описан выше. Отметки этапов относятся к реализации и автоматическим проверкам, а игровые критерии готовности подтверждаются отдельно по приёмочному листу.

- Приложение: обычные HTML/JavaScript, три объявленных окна (`background`, `overlay`, `desktop`), загрузка напрямую из `quicktype-overlay/`.
- В `background.html` открытие состоит из `restore`, `bringToFront(..., true)`, `requestOverlayFocus` и IPC. Используются общий `switching`, таймер 1200 мс и страховочный запрос фокуса через 60 мс; результаты части операций не проверяются.
- В `overlay.js` поле повторно запрашивает фокус сразу и через 15/45/100/200 мс. Таймеры проверяют видимость, но не поколение открытия: старая попытка может попасть в уже новую видимую сессию.
- Геометрия сохраняется абсолютными координатами; восстановление ограничивает размеры фиксированными пределами, но не проверяет актуальную доступную область. Сброс задаёт 640×100 и позицию (100, 100).
- На машине разработки проверена установленная версия Overwolf `0.311.1.1`. Минимальная версия приложения в манифесте — `0.250.0`; повышение минимума требует отдельного обоснования совместимостью API.
- ODK предлагает Promise-операции, позиционирование, DPI и привязку. В изученном исходнике `bringToFrontWithFocus()` оборачивает существующий `overwolf.windows.bringToFront(id, true, callback)`; это не доказательство нового механизма захвата ввода.

## Порядок реализации

Каждый этап — отдельное локальное изменение с проверкой перед следующим. Начать с этапов 0–1 на существующем API; решение об ODK принять на этапе 4.

### Этап 0. Зафиксировать исходное поведение

- [x] Через [Docs MCP](../../development/overwolf-docs-mcp.md) проверить Native API для фокуса, состояний, `setBounds`, мониторов и DPI; сверить необходимые версии клиента.
- [ ] Записать игру, графический API, оконный режим, раскладки, разрешение и DPI для воспроизводимого случая потери фокуса.
- [ ] Пройти базовую матрицу ниже на текущем приложении и сохранить наблюдения. Не считать отсутствие второго монитора или игры успешным тестом.
- [ ] Проверить доступность `overwolf://api-tracing` под developer account. При доступности использовать для порядка вызовов и ошибок; не записывать REST payload и авторизационные данные.

Готовность: есть исходный сценарий и результаты, позволяющие сравнить эффект изменения. Не менять GamesList или настройки игры автоматически.

### Этап 1. Управление жизненным циклом и фокусом

- [x] Ввести явное желаемое состояние и номер операции/поколения открытия. Запоздалые callbacks и таймеры предыдущей операции не должны снова активировать скрытое окно или новую сессию ввода.
- [x] Координировать показ/скрытие/повторный вызов из контроллера, исключить пересечение операций после произвольного таймера `switching`.
- [x] Обрабатывать ошибки `restore`, `bringToFront`, `requestOverlayFocus`, IPC и скрытия. Ограниченный timeout должен освобождать управление и позволять повторный вызов, без бесконечных повторов.
- [x] Разделить системный захват фокуса и DOM-фокус поля. Согласовать контроллер и оверлей. По уточнённому запросу пользователя реализация завершена до игровой приёмки; DOM-повторы сохранены, native-повторы из поля удалены.
- [x] Добавить регрессионные проверки на быстрый show/hide/show, поздний callback, отказ API и отсутствие callback, а также сохранность черновика и активного REST-запроса.

Готовность: после скрытия старые операции не возвращают фокус; новый вызов работает после отказа/timeout; Enter и Escape сохраняют текущую семантику. Реальный возврат управления игре подтверждён ручной проверкой.

### Этап 2. Восстановление видимой геометрии

- [x] Определять доступную область отдельно для рабочего стола и активной игры; учитывать рабочую область монитора, отрицательные координаты и различие физических/логических единиц.
- [x] Восстанавливать сохранённое положение, если оно доступно. Если монитор отключён или окно вне доступной области, переносить его в видимую область и ограничивать размер её размерами.
- [x] Заменить безусловный сброс в (100, 100) осмысленным размещением в текущем контексте, например по центру. Зафиксировать окончательный вариант в пользовательской инструкции.
- [x] Использовать `setBounds` для совместного изменения размера и позиции, если совместимость подтверждена. Учесть `auto_dpi_resize`; при необходимости оставить проверенный fallback на старых клиентах.
- [x] Обновлять сохранённую геометрию только после успешной операции. Сохранить различие ручного размера и автоматической высоты, совместимость старых настроек и независимое сохранение параметров подключения.
- [x] Покрыть расчёт геометрии тестами: отключённый монитор, отрицательные координаты, маленькая область, масштабирование, ошибка API.

Готовность: окно и его управляющие элементы доступны после смены конфигурации экрана; сброс и авторазмер работают, старые настройки читаются.

### Этап 3. Необязательная привязка к краю

- [x] Добавить явный выбор свободного размещения или привязки снизу по центру с отступом; текущим пользователям сохранить свободный режим по умолчанию.
- [x] В режиме привязки пересчитывать позицию после автоматического изменения высоты и смены доступной области. Ручное перемещение должно переводить окно в свободный режим и сохранять новое положение.
- [x] Автоматически проверить перенос текста, скрытие/открытие, геометрию при смене DPI/области; проверить Save/Reload настроек в браузере и обновить документацию. Реальные экраны и игры остаются в ручной приёмке.

Готовность: привязка не мешает вводу и не борется с ручным перетаскиванием. Можно отложить этот этап независимо от исправлений этапов 1–2.

### Этап 4. Изолированная оценка ODK и решение

- [x] Зафиксировать конкретную доступную версию `@overwolf/odk-ts` и её типы. Не полагаться на `main` как на опубликованный пакет. Изученный `package.json` на `main` содержит `1.1.2` и Node >=22; текущий CI проекта использует Node 20.
- [x] Проверить действительные сигнатуры: обзор показывает `Windows.self()/fromId()`, изученный исходник — асинхронные `Windows.Self()/FromId()`. Проверить поддержку оборачивания существующих объявленных окон.
- [x] Проверить сохранение всех нужных параметров: прозрачность, видимость на desktop/в игре, `grab_keyboard_focus`, takeover `ReleaseOnHidden`, release hotkey, размеры и taskbar.
- [x] Сделать локальный прототип вне подключённой папки `quicktype-overlay/`. Оценить подготовку браузерного JS, зависимости, воспроизводимость и возможность продолжать загрузку unpacked. Не собирать ZIP/OPK.
- [x] Сравнить контракт, модель геометрии/DPI, вызовы фокуса, обработку ошибок и стоимость сопровождения на изолированном прототипе; реальные показатели игровой матрицы оставить ручной приёмке.
- [x] Записать решение: внедрить ODK частично/полностью либо оставить прямой API. Полный перенос на TypeScript и динамическое создание всех окон не являются условием выполнения roadmap.

Готовность: решение обосновано результатами; перенос в рабочее приложение — отдельный небольшой шаг после успешного прототипа. Есть простой откат к предыдущему рабочему варианту.

## Матрица ручной проверки

Для каждого выполненного сценария фиксировать версию приложения/Overwolf, окружение, ожидаемый и фактический результат. Непроверенные варианты отмечать явно.

| Сценарий | Ожидаемый результат |
|---|---|
| Desktop: запуск, значок хаба, настройки | Окна открываются, доступны и не создаются повторно |
| Игра: borderless и fullscreen, если поддерживается | Хоткей открывает ввод; Enter/Escape возвращают управление игре |
| Быстрый хоткей, скрытие до callback, повторный вызов | Финальное состояние соответствует последнему действию; поздний фокус не возвращается |
| Alt+Tab, потеря фокуса, RU/EN при открытом поле | Нет нового перехвата после скрытия; поведение раскладки сравнивается с исходным |
| Медленный/ошибочный REST, скрытие и новое открытие | Черновик сохранён; старый ответ не стирает новый ввод и не закрывает новую сессию |
| Один/два монитора, монитор слева, отключение второго | Оверлей и настройки остаются доступны |
| DPI 100%/150%, разные DPI экранов, смена разрешения | Положение и размеры осмысленны; окно не выходит за доступную область |
| Ручной ресайз, несколько строк, сброс, Reload | Геометрия сохраняется; автоматическая высота не превращается в ручную случайно |
| OOPO / trusted fullscreen без интерактивного ввода | Ограничение платформы зафиксировано; отображение не выдаётся за работающий захват ввода |

## Проверки и завершение

- Синтаксис изменённых JS и встроенного скрипта `background.html`, целостность JSON и ресурсов манифеста, `node --test tests/regressions.test.cjs`.
- Тесты со заглушками подтверждают управление состоянием и геометрию, но не реальный exclusive focus. Игровую проверку выполнять после ручного Reload unpacked extension совместно с пользователем.
- Новые API и зависимости не должны молча повышать минимальные требования. Итоговый минимум и CI обновляются только при обоснованной необходимости внедрения.
- Обновить инструкции и changelog по фактическому результату. Перенести roadmap в `completed/` с Outcome после реализации обязательных этапов, решения по ODK и фиксации результатов ручных проверок; отложенные функции обозначить явно.
- Работа локальная; push и сборка дистрибутива — только по прямому запросу пользователя.
